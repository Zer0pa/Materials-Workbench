## What the wave verifies (and doesn't)

The wave verifies, for each of the 16 PRD-mandated deliberate failures:

1. **Input that should fail** — loaded from `fixtures/negatives/<case>/` for the 13 negative-fixture cases or generated by an in-process synthesizer for the 3 cases that are too narrow for a dedicated fixture (case 4 missing source manifest, case 7 DFT convergence delta, case 11 phase-field conservation violation).
2. **Exactly the right falsifier fires** — each case has a `target_falsifier` field naming the gate that MUST fire with `status="fail"`. The integration test asserts `cr.target_fired` for every case.
3. **No others fire spuriously** — `COFIRES` documents the small set of allowed paired triggers (PRD-mandated co-fires like `tenant_only_tuple_leak` correctly surfacing both `l7.tenant_only_tuple_leak` AND `l7.candidate_promotion_provenance`). Anything outside `COFIRES` is counted as a spurious extra and lowers the verdict from `correct` to `spurious`.
4. **Audit-chained proof** — every triggered FalsifierItem becomes a row in `falsifiers.jsonl` carrying the case name, target, expected layer, and the verbatim boundary block. Every case writes a Decision row to `decisions.jsonl`. Both chains validate after each case AND post-wave.

The wave does **not** verify:

- That positive-path fixtures still work end-to-end (that's the cross-layer integration tests in `tests/integration/campaigns/`).
- That layer adapters produce schema-valid envelopes on the happy path (that's the contract tests under `tests/contract/`).
- That GPU-bound layers parity-match between local_stub / runpod_mock (that's Wave 5c's hard-failure detectors and parity tests).

## Documented co-fires

A few negative fixtures legitimately fire more than one falsifier. These pairings are explicitly listed in `COFIRES` with rationale:

- `ionic_overclaim_no_service` → also accepts `l15.phonon_does_not_substitute_for_ionic` (the conductivity claim implicitly violates the L1.5 phonon-substitution boundary as well).
- `missing_source_manifest` → also accepts `phase0.kg_property_observation_written` (Phase 0 KG-write requires BOTH a LiteratureSource and a PropertyObservation node; a missing source manifest leaves both absent).
- `tenant_only_tuple_leak` → also accepts `l7.candidate_promotion_provenance` (a leaked tuple is, by definition, a rights-incompatibility violation — the PRD-mandated mapping is BOTH `A1 reasoner enforce_reuse_scope_export` AND `L7 candidate_promotion_provenance`).

Cases not listed must fire exactly one falsifier with status="fail" or the wave verdict drops to `spurious`.

## CLI

The `falsification` Typer subapp ships with three commands:

- `falsification run [--audit-dir PATH] [--fixtures-root PATH] [--report PATH] [--operator NAME] [--json|--text]` — runs the 16-case wave end-to-end. Writes `falsifiers.jsonl` + `decisions.jsonl` to the audit dir, persists the Falsifier KG nodes to `kg.sqlite`, and writes the markdown report. Exits non-zero on any missed case, spurious extra, or chain break.
- `falsification validate-chain [--audit-dir PATH]` — re-validates `falsifiers.jsonl` and `decisions.jsonl` after the fact (useful for CI after a separate run, or for validating an audit dir copied from another machine).
- `falsification list-cases` — pretty-prints the 16-case order with case name, layer, target falsifier, and source.

The lead agent wires `falsification_app` into `cli/main.py` after this wave. Standalone invocation works today via `python -m zer0pa_materials.cli.falsification ...`.
